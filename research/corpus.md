# What shell commands do Pi agents actually run?

Corpus analysis for the "should Pi ship its own portable bash (psh)?" question.
Generated by the scripts in `research/corpus/` (see *Reproduce* at the end). All
numbers are aggregates. Examples are generic paraphrases of the observed patterns,
not copies of real commands.

## 0. TL;DR

* **295,401 shell commands** from 6,112 sessions (Pi coding agent Mar–Nov 2026 and P2 Oct–Nov 2026).
  They all ran on **macOS**. No session ran natively on Windows and no P2 session used a remote env.
* **The two products run different shells.** The coding agent uses `/bin/bash` (bash **3.2** on macOS).
  P2 uses `$SHELL`, which is **zsh** on this machine, even though the tool is called `bash`. On P2,
  815 commands hit `zsh: no matches found` (an unmatched glob) and 92% of them still reported success.
* **The shell subset is small and regular.** Only 0.07% of commands fail `bash -n`. The syntax that
  matters is `&&` (55%), pipes (47%), `cd X && …` (46%), `;`/newlines (42%), `2>&1` (15%), quoted
  here-docs (13%, mostly `python3 - <<'PY'`), `$VAR`, `$(…)`, `>`/`>>`/`/dev/null` redirects,
  `for` loops (3.5%) and env prefixes (3.2%). `if`, `[ ]`, functions, `while`, `case`, arrays,
  `[[ ]]`, here-strings, process substitution, backticks and brace expansion are each ≤0.6%.
* **Utilities are concentrated.** The top 10 command names cover 52% of commands outright, the top 20
  cover 76%, the top 50 cover 92% and the top 100 cover 98%. A 117-name builtin set (shell builtins,
  coreutils, grep/rg/sed/awk/find/jq) can run **37.6% of commands fully in-process**. Adding one
  external program brings that to **85%**. The external programs are mostly `git`, `python3`, `node`,
  `npm`, `cargo`, `gh` and local scripts.
* **About half of all commands are pure reads** (51.7%), and **47% limit their output**
  (`| head` in 32%, `sed -n 'N,Mp'` in 13%). The agent uses the shell as its file viewer. On P2, `bash`
  accounts for 91% of tool calls; `read` gets 651 calls against 44.8k bash calls.
* **Few failures come from the platform, and many are hidden.** 5.1% of commands fail. About 1,000
  of those failures (≈7%, 0.34% of all commands) come from the shell or platform: missing `timeout`
  (GNU), GNU-vs-BSD flags (`cat -A`, `grep -P`, `sed -i <script>`), quoting/syntax errors, zsh glob
  errors and missing tools. Another ~1,300 commands printed a platform error but still **exited 0**,
  because the error came before `;`, inside `|| true`, or in a non-final pipeline stage. Only 0.3%
  of commands use `set -o pipefail`, while 47% use pipes.

## 5. GNU vs BSD sensitivity

The agents mostly write macOS-correct commands: `sed -i ''` appears 5,307 times against 144 GNU-style
`sed -i 's/…/'` (24% of those failed). The GNU-isms they reach for anyway are:

| pattern | commands | notes |
|---|---|---|
| `timeout N cmd` (GNU coreutils, missing on stock macOS) | 496 | **389 commands printed `timeout: command not found`**; most still exited 0 (`; echo`, `\|\| true`). P2 projects carry a `scripts/timeout.sh` shim (8k uses) |
| `cat -A` / `-vet` | 60 / 18 | 65 `cat: illegal option -- A` errors (`-A` is GNU-only) |
| `grep -P` | 21 | 22 `grep: invalid option -- P` errors |
| GNU `sed -i <script>` | 144 | 24% failed |
| `stat -c` (GNU) vs `stat -f` (BSD) | 398 vs 327 | both forms show up; the agents guess |
| `find -printf` | 48 | 10% failed |
| `readlink -f`, `realpath` | 36, 72 | |
| `nproc` vs `sysctl -n hw.ncpu` | 26 vs 63 | |
| `date +%s`, `-u`, `-v` (BSD), `-d` (GNU), `+%N` | 200, 167, 14, 2, 24 | |
| `sort -V`, `sort -h` | 58, 42 | |
| `xargs -0`, `-r` (GNU), `-P` | 243, 32, 35 | |
| `gtimeout` | 19 | 53% failed (not installed) |

The flag profile of the top utilities is narrow (Table T6b). `grep -n/-E/-v/-rn/-i/--include/-A N/-c/-o`,
`rg -n/--glob/-g/-i/-S/-C/-l/--type`, `sed -n` (56k uses) and `sed -i`, `head -N`/`tail -N` (the old

One quirk: arguments that begin with `--`, such as Pi's own session directory names

* Durations: median about **70 ms**. p90 is 15 s (agent) and 23 s (p2); p99 is 2.4 min and 4.4 min.
  13–17% of commands take over 10 s and 3.4–4.4% take over 60 s. Commands are bimodal: fast reads
  versus builds and tests.
* The model sets the tool's `timeout` argument on 57% of calls: ≤30 s 25%, ≤120 s 17%, ≤600 s 8.5%,
  >600 s 6%. Even so, 519 commands timed out. The most common ones run `node` scripts, `find` over
  large trees, `git`, `python3`, `curl` and docker. 218 were aborted by the user.
* Anecdote: while this analysis ran, several `python -m http.server` processes started by agent
  sessions were still running 4+ days later. Commands backgrounded with `&`/`nohup` outlive the
  tool call and are never cleaned up.

## 8. Windows and remote

* **No native Windows sessions.** Every session cwd is a macOS path. The P2 catalog has 39 sessions,
  all with a local env (none remote). There are no `C:\` cwds, Git Bash, or "is not recognized as an
  internal or external command" errors from a Windows host.
* Windows work was done **from macOS through Parallels**: 254 `prlctl` commands, 112 of them
  `prlctl exec "Windows 11" powershell|cmd /c|node.exe …`, plus `prlctl` into an Ubuntu VM.
  17 of the 112 Windows commands failed (15%), about three times the base rate. The causes were
  PowerShell parser errors from quoting across bash → prlctl → PowerShell (bash expanding `$x`
  intended for PowerShell, unbalanced parentheses), timeouts on large downloads in the VM, Node
  module resolution on `\\Mac\Home\…` UNC paths, and WSL not being installed. 161 commands mention
  `powershell`/`pwsh`, 33 use `cmd /c`, and 14 mention `wsl`.
* Remote: `ssh` appears in only 7 commands and `scp`/`rsync` in 47. Containers are more common:
  `docker run`/`exec` in 1,217 commands.
* So the corpus says nothing directly about how agents behave on a Windows host. The indirect evidence
  is that a model writing for Windows still writes bash-isms, and the nested-quoting failures when
  driving PowerShell from bash are one of the more frequent shell-attributable error classes.

## 9. Implications for psh

1. **Pick one shell and make it the same everywhere.** Pi agent (bash 3.2) and P2 (zsh, via `$SHELL`)
   already differ. The zsh nomatch behaviour alone produced 815 broken commands that mostly looked
   successful. A bundled psh with bash semantics (unmatched globs stay literal) removes this whole
   class of errors.
2. **Grammar scope**: lists, pipelines, redirects/fd-dup, quoted here-docs, `$(…)`, parameter
   expansion with the common operators, `for`/`if`/`test`, env prefixes, subshells and background
   jobs. That covers more than 99.5% of the commands, and tree-sitter-bash is good enough for
   classification (0.04% false parse errors).
3. **Builtins worth doing in-process**, in order of use: `cd head grep rg sed tail cat echo ls find
   printf wc sort rm true cut cp awk mkdir mktemp jq uniq nl tr seq xargs diff date sleep timeout
   pwd test basename stat tee ln`. They should accept both GNU and BSD spellings: `sed -i ''` and
   `sed -i`, `stat -c` and `-f`, `cat -A`, `grep -P`, `readlink -f`, `date -d` and `-v`, `xargs -r`.
   A real `timeout` builtin alone fixes the most common "command not found" (389 commands).
4. **Report status per pipeline stage, and surface stderr errors even when the final status is 0.**
   About 1.3k commands hid platform errors behind exit 0. Exit status is a weak signal because of `;`
   chains, pipes without pipefail, `|| true` and `2>/dev/null`.
5. **Output limiting is the main "feature"**: 47% of commands cut output with `head`/`tail`/`sed -n`.
   In-process `head` with early pipeline termination is cheap. Built-in truncation could make many of
   these pipes unnecessary.
6. **cwd handling**: 46% of commands begin with `cd`, and 56% of those cd into the directory they are
   already in. A documented, persistent cwd per call would save tokens.
7. **Process lifecycle**: background jobs, `nohup` and dev servers (≈1% of commands) need tracking and
   cleanup when the tool call or session ends. `sleep`/poll loops (4%) suggest a "wait for
   port/file/output" primitive would help.
8. **Classification**: 51.7% of commands are statically pure read-only; that set can be auto-approved
   or sandboxed cheaply. Inline interpreters (13%: python/node here-docs, `-c`/`-e`) and local scripts
   (17%) cannot be classified without looking inside them.

## Reproduce

```
cd research/corpus
python3 extract.py            # -> ~/.cache/psh-corpus/commands.jsonl (PRIVATE: raw commands + output snippets)
uv venv .venv && uv pip install --python .venv/bin/python tree-sitter tree-sitter-bash
.venv/bin/python analyze.py   # tree-sitter-bash parse -> ~/.cache/psh-corpus/features.jsonl (PRIVATE)
python3 syntaxcheck.py        # bash -n / zsh -n ground truth (parse only, nothing executed)
python3 report.py             # -> research/corpus/results.json (aggregates only)
python3 render.py             # -> research/corpus/tables.md (all tables below)
```

Caveats: the categories and failure kinds are heuristics (name/flag rules plus output regexes), so
treat them as approximate. "Commands" means tool calls. One call may contain many simple commands.
Codemode nested calls have no exit codes. Feature counts come from the tree-sitter AST. The
GNU/BSD flag patterns and the long-running patterns are regexes on the raw command text.
